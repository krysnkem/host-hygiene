# Web frontend / monorepo developer

## Entries

### monorepo-node-modules
- what: workspace repos (npm/yarn/pnpm workspaces, Turborepo, Nx) with a root node_modules plus one per package or app
- catalog-id: none
- paths: <repo>/node_modules, <repo>/packages/*/node_modules, <repo>/apps/*/node_modules
- size: (unverified); hoisting puts most deps at the root, pnpm keeps a symlink farm into its store (pnpm docs: https://pnpm.io/workspaces)
- class: safe-regenerable
- removal: rm-verified on every node_modules in the repo (after git confirms ignored), then one install at the root
- regen: one root `install` rebuilds all; do not delete only some, hoisting can leave dangling links. With pnpm the files are hard links into the store, so real freed space is small until the store is pruned
- growth: multiplies with workspace count; non-hoisted conflicts add nested copies. Suggested: purge repos idle over 60 days (suggested)
- source: https://pnpm.io/workspaces ; sizes (unverified)

### storybook-cache
- what: Storybook's build and dev caches, and static output
- catalog-id: none
- paths: <project>/node_modules/.cache/storybook (Vite builders also node_modules/.cache/.vite-storybook or sb-vite, community-reported); <project>/storybook-static
- size: (unverified)
- class: safe-regenerable
- removal: rm-verified after git confirms ignored (storybook-static is normally ignored build output)
- regen: next `storybook dev` or `build-storybook` is a cold build, minutes
- growth: per project, grows with stories and addons
- source: community-reported only, via search 2026-11-17 (Storybook issue threads and https://tessl.io/registry/tessl/npm-storybook--core-common/8.6.0/files/docs/caching.md mirror: delete node_modules/.cache/storybook, or use `--no-manager-cache`); Storybook's official CLI-options page (https://storybook.js.org/docs/api/cli-options) mentions neither the cache dir nor the storybook-static default, so unconfirmed officially (unverified)

### chromatic-artifacts
- what: Chromatic visual-test local artifacts and logs (the snapshots live on Chromatic's servers)
- catalog-id: none
- paths: <project>/chromatic-diagnostics.json, <project>/build-archive.log, <project>/storybook-static
- size: (unverified)
- class: safe-regenerable
- removal: rm-verified of the log files after checking they are ignored
- regen: regenerated by the next `chromatic` run; baselines are not stored locally
- growth: small except storybook-static
- source: reported online, https://www.chromatic.com/docs/cli (fetched 2026-11-17: only `--diagnostics-file` writing chromatic-diagnostics.json is confirmed; build-archive.log and storybook-build.log are not mentioned there, so those names stay (unverified))

### docker-web-layers
- what: Docker image layers and build cache from web app images (node base images, multi-stage `npm ci` layers, nginx images)
- catalog-id: none
- paths: ~/Library/Containers/com.docker.docker
- size: (unverified); see the Docker entry in the Backend KB when written
- class: ask-first
- removal: docker builder prune (build cache only, safest first); docker system prune
- regen: images re-pull and layers rebuild, each `npm ci` layer re-downloads dependencies; named volumes hold data, never use --volumes without asking
- growth: each Dockerfile edit above the COPY package.json line invalidates the install layer and adds a new layer. Suggested budget 20 G for the Docker disk image (suggested)
- source: https://docs.docker.com/reference/cli/docker/builder/prune/ ; sizes (unverified)

### deno-cache
- what: Deno's module, npm-compat and compile cache (DENO_DIR)
- catalog-id: deno-cache
- paths: ~/Library/Caches/deno (macOS default; DENO_DIR overrides; older releases used ~/.deno)
- size: absent here (measured here, deno is installed via Homebrew); typical size (unverified)
- class: safe-regenerable
- removal: `deno clean` (documented: removes the global module cache dir; `--dry-run` previews, `--except <entrypoint>` keeps what it needs; introduction version not stated, check `deno clean --help` on the installed one), or rm-verified of the cache dir
- regen: remote and npm: modules re-download on next run; offline scripts fail until then
- growth: grows with every remote import and npm: package version; no eviction
- source: reported online, https://docs.deno.com/runtime/fundamentals/installation/ (macOS $HOME/Library/Caches/deno, via search result 2026-11-17, page itself not read) and https://docs.deno.com/runtime/reference/cli/clean/ (fetched 2026-11-17); size absent here measured on this host 2026-11-17

### bun-global-and-runtime
- what: bun's own install dir: binary, global packages, caches
- catalog-id: none
- paths: ~/.bun (bin, install/cache, install/global)
- size: 123 M total (measured here)
- class: ask-first
- removal: bun pm cache rm for the cache only (or `bun pm cache prune` for entries older than 30 days); never rm the whole ~/.bun, it holds the bun binary and `bun add -g` tools
- regen: cache refills on install; global tools must be re-added
- growth: dominated by the cache, 62 M here (see bun-cache in node-typescript.md)
- source: measured on this host 2026-11-17; reported online, https://bun.sh/docs/pm/cli/pm (fetched 2026-11-17)

## Developer habits
- Monorepos: one install per repo, but dozens of packages each with node_modules, .turbo, .next and dist.
- Mixed tooling: Storybook plus Chromatic for visual review, Docker for deploy images.
- Several runtimes tried side by side: Node, Bun, Deno.

## Signals
- pnpm-workspace.yaml, package.json `workspaces`, turbo.json, nx.json, lerna.json
- .storybook/, storybook-static/, chromatic config in package.json scripts
- Dockerfile with `npm ci` or `pnpm install`; deno.json, bunfig.toml

## Not covered / open questions
- No monorepo of this shape was measured on this host, so per-repo sizes are all unverified.
- Storybook cache dir name is community-reported only; Chromatic build-archive.log is unconfirmed (see entries).
- Turborepo: docs state local cache is `.turbo/cache` (https://turborepo.dev/docs/crafting-your-repository/caching, fetched 2026-11-17); no global cache dir or clean command is documented there, so no entry added.
- Vercel CLI: global config/auth lives in ~/Library/Application Support/com.vercel.cli per search of Vercel's global-configuration docs (config, not a cache; no local cache dir found). Netlify CLI: global config.json at Library/Preferences/netlify on macOS (config, holds the token, never remove); no cache dir found. No entries added.
- Nx daemon and Rush/Lage were not researched.
